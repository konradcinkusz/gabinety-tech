# ADR-0010: A Blazor Web App is the product surface (static rendering by default, interactive server per page)

- Status: proposed (the owner moves it to `gabinety-tech-spec/docs/adr/` and sets it `accepted`; it is written against the template `docs/adr/0000-template.md` of that repository)
- Date: 2026-11-22
- Supersedes: ADR-0001 (Next.js with a backend-for-frontend) and DECISIONS D-32 ("Next.js with a BFF"), once accepted
- Deviates from: `BLAZOR-WEB-APP` section 3 (root-level interactive render mode), see Decision 2

## Context

ADR-0001 chose Next.js and **rejected Blazor** because "the product is an anonymous, SEO-driven, scaled surface". The standards say the same thing from the other side (`BLAZOR-WEB-APP` section 1): Blazor suits a bounded audience, a team that writes C#, a modest page count; Next.js suits a public, horizontally scaled, SEO product. By that guide this product is the Next.js row, not the Blazor row.

The owner has now asked for the frontend to be ported to a Blazor Web App and has overridden ADR-0001's reasoning explicitly. That is the deciding input. This ADR records it, says which risks it knowingly takes, and fixes what the port must do so that those risks are mitigated rather than ignored.

**The row of `BLAZOR-WEB-APP` section 1 that decided it** is the *Toolchain* row: "`.NET SDK only; no Node, no JS dependencies`" against "`Node, pnpm workspace`". Every service, the kernel, the AppHost, the seeder and the identity stand-in are .NET; the web app is the one place with a second language, a second package manager, a second test stack (vitest, testing-library, jsdom) and a second CI job. It is **not** decided by the *Best fit* row: this is a public, SEO-driven product and the guide does not recommend Blazor for it. The owner accepts that; this ADR does not pretend otherwise.

## Decision

1. **`src/Gabinety.Web` is a Blazor Web App** (`Microsoft.NET.Sdk.Web`, `net10.0`), the host of the product's pages, with interactive server rendering available. It references `Gabinety.ServiceDefaults` and `Gabinety.ServiceDefaults.Edge` and nothing else; no NuGet package of its own (the ASP.NET Core shared framework only), no JavaScript package, no component library, no CSS framework, no web font. Blazor WebAssembly is not used (it puts the API address and the token in the browser). The Next.js app in `web/` is untouched and keeps working until a cutover PR; both run in the fake profile (Next.js on 3000, Blazor on 3001).

2. **Static server rendering is the default; `@rendermode InteractiveServer` is applied per page, only where interaction is needed** (the booking flow, forms that need it, authenticated areas). `App.razor` puts **no** render mode on `Routes` and `HeadOutlet`, which is the opposite of `BLAZOR-WEB-APP` section 3. Reasons: (a) the public pages must be real HTML for crawlers and with JavaScript disabled (journey J1 asserts it); (b) a root-level interactive mode puts a circuit under every anonymous visitor and every crawler request, and per-circuit memory is the capacity limit (guide section 14); (c) a static page costs nothing to keep open. The guide's pins ("`Routes` and `HeadOutlet` carry the interactive mode") are therefore **reversed** and pinned the other way (`RenderModeTests`): the roots carry no render mode, exactly the listed pages carry `InteractiveServer`, no public page does, and an interactive page really starts a circuit (the prerendered HTML holds a server component marker) while the home page and the lists contain none. Validated in .NET 10 and pinned by tests: per-page render modes with prerendering; `[SupplyParameterFromQuery]` in static pages (the list's filters, the shareable view of "my bookings"); `[SupplyParameterFromForm]` with `EditForm` and antiforgery in a static page (sign-in and sign-out work with JavaScript disabled); `NavigationManager.NotFound()` for the 404 of an unknown category; a cascading `HttpContext` in a static page (sign-in, the visitor address); `Router` with `NotFoundPage` and status-code re-execution.

3. **Sessions and authentication** follow `BLAZOR-WEB-APP` section 7. Cookie authentication on the host (`gt_session`: `HttpOnly`, `SameSite=Lax`, host-only, `Secure` when `Site:BaseUrl` is https: the attributes of the Next.js cookies). The cookie holds only an opaque session id; the identity service's tokens stay in a server-side store. The token is verified (RS256 signature against the JWKS, expiry, issuer and audience when configured) before a cookie is issued. The three Blazor traps are handled: no `HttpContext` in components (the user comes from the `AuthenticationStateProvider`); the token reaches the `HttpClient` through `HttpRequestMessage.Options` from the client wrapper, which runs in the circuit's scope, because message handlers have their own scope; a circuit that outlives the cookie ends at its next revalidation (one minute). Every route requires a session unless it says `[AllowAnonymous]` (the kernel's fallback policy, as in the services), with a route-audit test and rows in `docs/operations/ROUTE-AUTH.md`. `[Authorize]` is UX; the services remain the boundary and every call carries the user's bearer.

4. **Backend calls**: one typed client per backend (Directory, Booking, Reputation, Assistant, plus the identity client), logical base addresses resolved by service discovery from the same `Backend__*` variables the Next.js app reads, exactly one resilience handler (the kernel's, tuned to SPEC 5.1: 5 s, one retry, `GET` only), errors as state in a `role="alert"` block. The visitor's address goes to the services in `X-Client-Address` with `X-Edge-Key` (`RateLimit__TrustedProxyKey`, PR #110), so per-visitor limits key on the visitor. **DTOs are copies** in the web project, not a reference to `Gabinety.Contracts` (SPEC 3.2 gives the web no edge to it, and the guide's rule is that the contract is HTTP); a round-trip test serializes the real contract types and reads them into the copies, so a renamed field is a failing test.

5. **Requests from another site** (`BLAZOR-WEB-APP` section 8): one guard in `Gabinety.ServiceDefaults.Edge` (the kernel is at 400 of 400 lines), first in the pipeline, for every method and path: a foreign `Origin` is refused (so a foreign page cannot negotiate a circuit or upgrade the websocket), `Sec-Fetch-Site: cross-site` is refused except a top-level `GET`/`HEAD` navigation, no `Origin` is allowed; `403 cross_site_request`, the code of CONTRACTS 10.1 and of journey J7. CORS stays unconfigured. It is a mitigation, not authentication.

6. **Security headers** reproduce the intent of PR #113 (`SecurityHeaders` documents each difference): `script-src 'self'` and `style-src 'self'` (no nonce, no `'strict-dynamic'`, never `'unsafe-inline'` or `'unsafe-eval'`: the framework script is a same-origin file and no page has an inline script or style), `connect-src 'self'` plus this host's own `ws:`/`wss:` origin (the circuit), `frame-ancestors 'none'`, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, the permissions policy, `X-Frame-Options: DENY`, HSTS only where the site is https.

7. **Styling** is a neutral token sheet (`wwwroot/tokens.css`, both themes), shared classes (`wwwroot/app.css`) and one scoped `Foo.razor.css` per component, pinned by a stylesheet test (colour only through tokens, both theme blocks, AA contrast of the text pairs, focus, reduced motion) and by a test that the scoped bundle is linked and served. The real design contract (`docs/ui/DESIGN-CONTRACT.md`, `docs/ui/tokens.css`, written in parallel) replaces `tokens.css` and nothing else.

8. **Amendment (2026-11-22, owner decision D-1 of `docs/ui/UX-PLAN.md`): one first-party enhancement script.** `wwwroot/enhance.js` is allowed (same origin, no dependency, `script-src 'self'` already covers it). It only adds live character counters, a pending state on a submitted button, a modal dialog for states that also live in the URL, show-password, copy link and auto-submit of a filter select; every page works without it. Chosen over an interactive circuit per page, which costs a websocket per visitor and reacts with network latency.

## Consequences

**Hosting** (`BLAZOR-WEB-APP` section 14). A stateful frontend keeps every open interactive page in server memory over a websocket.
- Websockets must pass Fly's proxy, and idle timeouts must exceed the keep-alive interval.
- `min_machines_running = 1` and **no** idle stop for `gabinety-web-staging` (SPEC 4.3 already says 1: it is on the synchronous path of every page). Scale-to-zero (P7) is not available for this app: a stopped machine ends every circuit.
- **One instance, or session affinity.** A circuit's websocket and its follow-up requests must reach the same machine. Run one instance until there is a reason not to. The server-side session store is in memory, so a second instance is also a different set of sessions.
- **Data Protection keys must be shared and persisted** (`DataProtection__KeysPath` on a volume), or every deploy invalidates open forms (antiforgery) and the cookie. A Fly volume binds the app to one machine, which is consistent with the previous point.
- Behind Fly's proxy set `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` (so the scheme is https) and `Site__BaseUrl` to the public address (the guard allows exactly that origin; `AllowedOrigins` adds more).
- **A deploy or a restart ends every circuit and every session.** The Next.js cookies survived a deploy; these do not (the tokens are in process memory). Signed-in users sign in again after each deploy. Persisting the session store is possible later and is not in this ADR. The cutover signs everybody out once.
- Per-circuit memory is bounded by configuration (`Circuit__DisconnectedMaxRetained`, `Circuit__DisconnectedRetentionSeconds`, `Circuit__MaxBufferedRenderBatches`, `Circuit__MaxReceiveBytes`). Public pages and crawler traffic never create a circuit.
- The image is the standard multi-stage .NET one (`src/Gabinety.Web/Dockerfile`, non-root, `:8080`, `/alive`), with no Node stage. It has a CI build row; it is **not** in `deploy/estate.conf` yet (cutover).
- **No page cache.** The Next.js app caches each Directory read for five minutes (SPEC 6.5). The Blazor host calls the Directory on every public request (the list makes three reads). The services' read limit is per client address (120 per minute), which the forwarded visitor address protects, but a cache for anonymous `GET`s (output caching with a five-minute policy, varied on the session cookie) is a follow-up and should land before the cutover.

**SEO mitigation.** The home page and the public lists are static server rendering: the first response holds the content (`curl` with no JavaScript shows it; the page tests assert it). One `h1`, unique title and description, canonical (a variant points at the plain list), `noindex,follow` under three approved practitioners and on every filtered or paginated variant, `503` (not a `200` error page) when the Directory is down, a `404` status for an unknown category. The framework script is loaded on every page and is progressive enhancement. Not yet ported, and needed before the cutover: the profile page with its JSON-LD, `sitemap.xml` and `robots.txt`, the static pages. If measured organic traffic regresses, the fallback is the hybrid the owner can choose later: Next.js for the public pages, Blazor for the signed-in areas.

**Test layer.** vitest, testing-library and jsdom for the web app become xUnit, bUnit (component tests, **a new test-only package**: `bunit`, requested in the PR) and `WebApplicationFactory` host tests (render mode pins, styles bundle, origin guard, route audit, headers, navigation order, sign-in), all with fake handlers and no network. The Playwright journeys stay (TypeScript, `tests/e2e`, their own job) and point at this host with `E2E_WEB_URL`; the pages carry the same roles, names and a `data-testid` where one helps. J1's public-list steps map directly (the profile page is not ported). J7 posts through `/api/proxy/...`, a BFF route the Blazor host does not have (the browser never calls a backend): the same expectations (`403`, `cross_site_request`, nothing changes, a same-origin control passes) are pinned by `OriginGuardHostTests` against this host's own endpoints. Node remains only for the e2e harness.

**i18n.** One Polish catalogue in one place (`Text/Pl.cs`), strings copied verbatim from the Next.js catalogue so journeys that find things by name run against either host; a test fails on a Polish character anywhere else in the project (SPEC 5 rule 1). No resource files and no `IStringLocalizer`: the product has one language; a second one is an ADR.

**Cost.** One toolchain instead of two (no `pnpm`, no Node in the web image, one CI job fewer once `web/` goes), and every page now a server render on a machine that must stay up: memory per open interactive page is the capacity limit and has not been measured. It is to be measured with the performance script (T-10.04) before the cutover and `docs/operations/COST.md` re-checked. The web machine stays at 512 MB (SPEC 4.3) until measured.

**Contract drift.** SPEC 5 rule 9 (types generated from OpenAPI) disappears for the web app: the guard is the round-trip test of the DTO copies. A service that changes a field the web reads must change the copy in the same pull request, or that test fails.

**What stays the same.** The browser talks to its own origin only and never holds a token or a backend address; authorization is on the server; cookies are `HttpOnly`/`SameSite=Lax`; the public site has no third-party script; the services are untouched (no new route, no change to the origin guard of the kernel).

## Cutover preconditions (supervisor, 2026-11-22)

- **Deploys must not sign users out.** The in-memory session store in this foundation is accepted for the foundation only. Wave 2 replaces it with a stateless encrypted session cookie: the refresh token sealed with Data Protection using the persisted, shared key ring, the access token re-minted on demand.
- **Short output caching** (five minutes, by route and query, public anonymous pages only, never when a cookie or session is present) lands with the wave-2 public pages.
- Wave-2 auth requirements from the authservice session: password rules shown on registration; the Playwright harness parametrised per host (`BASE_URL`, `HOST=next|blazor`) with a Blazor variant of J7 against `/logowanie`. Already in the gateway and tested: the visitor address in `Fly-Client-IP` on server-to-authservice calls, a 429 on refresh does not end the session, the role claim as a string or an array with `Admin` or `SuperAdmin` counting as admin.

## Alternatives considered

- **Stay on Next.js (ADR-0001).** The standards' recommendation for a public, SEO-driven, horizontally scaled product, and stateless to host. Rejected by the owner's instruction; the Toolchain row is the reason.
- **Blazor with the interactive mode on the roots (`BLAZOR-WEB-APP` section 3 as written).** Simplest to write and the guide's default. Rejected: no content for a crawler or a visitor without JavaScript before the circuit connects, and a circuit per anonymous visitor.
- **Blazor WebAssembly.** Not supported by the standards: the API address and the token would be in the browser.
- **Static rendering only, no interactive pages.** Possible for the public site, too limiting for the booking flow, the assistant and the dashboards.
- **Hybrid: Next.js for the public pages, Blazor for the signed-in areas.** The lowest SEO risk and two frontends for good. Kept as the fallback above, not chosen.
- **Tokens in the encrypted cookie instead of a server-side store.** Survives a deploy, but a circuit cannot refresh a token (it has no response to set a cookie on) and the single-use refresh token makes concurrent refreshes unsafe without a lock that lives on the server anyway.

- **SPEC 3.2**: the `web/` row of the tree becomes `src/Gabinety.Web/` (Blazor Web App); **add the allowed edge** `Web → ServiceDefaults, ServiceDefaults.Edge` (and `Gabinety.ServiceDefaults.Edge`, which the tree does not list yet); in the dependency budget replace the `web` row (`next`, `react`, ...) with "`Gabinety.Web`: none, the ASP.NET Core shared framework only", add `bunit` to the tests row, drop `openapi-typescript` and the node packages from the web row after the cutover; `AppHost` → `Gabinety.Web`.
- **SPEC 4.1 and 4.3**: the `web` resource (a project, `/health`, port 3000 at the cutover; 3001 until then) and its Fly row (websockets, `min_machines_running = 1`, no idle stop, one instance or affinity, a volume for the Data Protection keys).
- **SPEC 5 rule 9** (generated types) and **rule 12** (the guard now lives in `ServiceDefaults.Edge` for the web host), **6.5** (the BFF paragraph: no `/api/config`, `/api/auth/*`, `/api/proxy/*`; the pages table is unchanged), **11 "Web"** (cookie name and the server-side session; the CSP differences listed above), **10** (web tests).
- **SPEC 12.1 A-16** (the Aspire JavaScript hosting integration starts the Next.js app): void at the cutover; the AppHost then drops `Aspire.Hosting.JavaScript` and `AddJavaScriptApp`. While both frontends run, A-16 still holds for `web/`.
- **CONTRACTS 7** (the BFF routes) is obsolete for this host; **10.3** `Backend:*` stays, with the note that the candidates are now service-discovery endpoints of one service, in order, instead of a probed ladder.
- **DECISIONS**: D-32 superseded by this ADR (a decision-log row with the date and the reason); **ADR-0001** status `superseded by ADR-0010`.
- **TASKS**: the pages not yet ported (the profile with JSON-LD, registration and the account page, the booking flow and checkout, the practitioner area, the admin area, the static pages, `sitemap.xml`, `robots.txt`, the GitHub exchange behind `/oauth/callback`), the output cache, memory measurement, the cutover PR (`deploy/estate.conf`, `deploy/fly/web.fly.toml`, the e2e base URL, retiring `web/` and the `web` CI job in the same change), `docs/operations/` (RUNBOOK, DEPLOY, COST).
