# Runbook (T-10.05)

Owner's operating procedures for staging on Fly.io. Written from the code of this repository at `f20b908`, the spec (`SPEC` §4.3, §8, §11, `CONTRACTS`), `AUTH.md` and `deploy/fly/`. Nothing here is secret; `<placeholders>` are filled by the owner.

## 1. How to read this document

**Every step carries a tag.** `[run: where, when]` means a person or an agent did exactly that step and saw its result. `[not run: reason]` means nobody did; the step is derived from code and documentation and is **unverified**. A `[not run]` step may be wrong in a flag, a path or an assumption about Fly; the first person to run it corrects this file and changes the tag.

State when this was written (2026-11-18): no Fly account or app exists (T-09.01, T-09.02, T-09.03 not done), the payment provider is the mock (T-09.05), no real booking has happened on staging (T-09.08), and the authoring session had no .NET SDK, so no service was started. Therefore only the backup, restore and retention steps of section 2 were run, and only locally on synthetic data. Everything else is `[not run]`.

Names: apps are `gabinety-<name>-staging` (`web-blazor`, `directory`, `booking`, `reputation`, `assistant`, `authservice`, `postgres`, `backup`); services listen on 8080 on the private network (`<app>.internal:8080`); only `web-blazor`, `authservice` and Booking are public (SPEC §4.3); Booking's public listener serves only the webhook, `/alive` and `/api/v1/*` except `/api/v1/admin/*`, everything else including `/internal/*` is 404 from the edge (F-03, `src/Gabinety.Booking/PublicEdge.cs`). Directory, Reputation and Assistant have no public address (`scripts/deploy/assert-no-public-ip.sh` fails the deploy otherwise). `fly` is the Fly CLI; every command takes `-a <app>`.

## 6. Payment webhook failure burst

|---|---|---|
| 401, many | no secret configured (every deployed provider is not Mock, so a missing `Payments__WebhookSecret` rejects all of them), or the signature does not verify (Stripe: the `Stripe-Signature` timestamp is more than 5 minutes off the Booking clock, or the signing secret is another endpoint's) | Warning `Webhook for {Provider} rejected: no webhook secret is configured`; for a bad signature an Error `ALERT payment webhook signature failure for {Provider}: event {ProviderEventId}` (event id 4301) |
| 200 `Rejected` | `PaymentSucceeded` whose amount or currency differs from the booking | Error `ALERT payment amount or currency mismatch for booking {BookingId}: expected ..., got ...`; the event is stored with outcome `Rejected` |
| 503 `dependency_unavailable` + `Retry-After` | Directory unreachable (the meeting-link lookup before confirming) | none specific |
| 202 `RetryLater` + `Retry-After` | the payment/booking row is not committed yet | none |
| 200 `Duplicate` / `Ignored` / `Applied` | normal: the event id was seen / unknown kind / applied | none |
| 413 | body over 64 KB | none |

## 7. A stuck job

Booking runs `hold_expiry`, `auto_complete` and `payout` as hosted services on a 60 s timer (`Jobs:IntervalSeconds`, default 60; first run one interval after start; `src/Gabinety.Booking/Jobs/Base/PeriodicJob.cs`). Booking also runs the stats push and the notification dispatcher, and Reputation runs the summary push, each on its own 60 s loop. Jobs are idempotent and safe in two processes at once, so **running a job again is always allowed**.

| # | Step | Tag |
|---|---|---|
| 7.1 | See it. Metrics (OTLP): `gabinety_job_lag_seconds{job}` (how late a cycle started; SPEC alert: over 10 minutes) and `gabinety_job_runs_total{job,outcome}` with `outcome=error`. No alerting product is wired in the MVP: read the logs: `fly logs -a gabinety-booking-staging \| grep -E 'Job .* run failed\|could not (expire\|complete\|be processed)\|Payout'`. | 7.2 | Symptoms by user effect: holds not expiring (a `PendingPayment` booking past `hold_expires_at` still blocks the slot, `bookings_no_overlap`); `Confirmed` bookings not completing 48 h after the end; payouts not sent. ## 8. GDPR erasure across authservice and the three hooks

Order (SPEC §8): authservice deletes the account, then the owner calls the erasure hook of Directory, Booking and Reputation with the user's id. Ledger rows, payments, payouts, ratings and the booking's amounts, statuses and times are **kept** for accounting (assumption A-13); personal and free text is replaced.

**Get the user id first.** It is the token subject (`sub`) of the account, and every hook is keyed by it. After authservice has deleted the account you cannot ask authservice for it. Record it while the user is still known (the person's own token, or authservice's admin API: its route for looking a user up is not documented in `docs/spikes/authservice.md`, section 11 question 4).

## 9. A suspended practitioner with future bookings

**Implemented (ADR-0012, supervisor decision 4).** Suspension: an administrator calls `POST /api/v1/admin/practitioners/{id}/suspend` with `{ "reason": "<10 to 500 characters>" }` on Directory (from `Approved`; `reinstate` goes back). The profile is hidden and **Booking refuses new bookings and shows no slots** (it reads the status through the offering lookup: `422 practitioner_not_bookable`). Directory saves the status first and then calls Booking, `POST /internal/v1/practitioners/{id}/cancel-future-bookings` (key `Internal__Keys__Booking` on Directory, `Internal__Callers__Directory` on Booking). Through the normal transition machinery (`BookingTransitions`, `RefundCoordinator`; CONTRACTS 8.1, 9.2) Booking then: moves **every `Confirmed` booking that has not started** to `CancelledByPractitioner` with a **full refund** (ledger `Refund`, no fee, no payout, `status_reason = practitioner_suspended`, not counted in `practitioner_cancel_count`, unlike a voluntary practitioner cancel: ADR-0012); **expires every unpaid hold** at once (a payment that arrives later is refunded in full by the existing paid-after-expiry rule); leaves bookings that have started or ended to run their course. The client gets the existing `Cancelled` notification (Polish template of `NotificationTemplates`), and the unsent reminders and the review request are removed. The call is idempotent. An erasure (section 8.2) first makes the same call and erases only after it succeeded: when Booking cannot finish, Directory answers `503` and the row is left whole, so the erasure job repeats the call.

## 10. Reaching a private app

`fly proxy <local>:<remote> -a <app>` forwards a local port to the app's private port: `15432:5432` for PostgreSQL, `18080:8080` for a service. It needs `flyctl` logged in as the owner. `[not run: no Fly account]`

## 12. The web host (`gabinety-web-blazor-staging`, the Blazor Web App, ADR-0010)

Read `DEPLOY.md` section 5 first. This is the one stateful app (open circuits in memory, the Data Protection keys on a volume), so its failure modes differ from the stateless backends'.

| Symptom | Likely cause | Do |
|---|---|---|
| Everybody was signed out | the session cookie is sealed with the Data Protection key ring (stateless, ADR-0010), so a deploy or restart must NOT sign anybody out: the key ring changed (the volume was recreated or not mounted) or `DataProtection__KeysPath` moved | `fly ssh console -C "ls -l /data/keys"`; restore the volume or accept the one-time sign-out and say so in the release note |
| Open forms fail with a validation or antiforgery error after a deploy | the Data Protection keys are not on the volume | `fly ssh console -C "ls -l /data/keys"`: empty or not writable means the volume is missing or not owned by `app`: `fly ssh console -C "chown -R app /data"`, restart |
| Pages load but do nothing (buttons, forms on interactive pages) | the circuit did not connect: websocket blocked, or `Site__BaseUrl` is wrong so the origin guard refuses `/_blazor` | browser DevTools, Network, WS; `fly logs` for `cross_site_request`; fix `Site__BaseUrl` |
| 503 from the proxy under load; memory near 512 MB | too many circuits (`COST.md` and `PERFORMANCE.md` give the measured capacity) | lower `Circuit__DisconnectedMaxRetained` / `Circuit__DisconnectedRetentionSeconds`, or `fly scale memory 1024`; the proxy `hard_limit` of 200 connections sheds before the machine dies |
| 429 for every visitor | `RateLimit__TrustedProxyKey` differs from the backends', so the visitor address is not trusted | set the same value on all five apps (section 5) |
| The machine is stopped | someone ran `fly machine stop` / `fly scale`; auto-stop is off | `fly machine start`; circuits are gone and come back by reload |

Memory: `fly machine status <id>` and `fly logs`; the host exposes the kernel's `/health` and `/alive` only. Never run more than one machine without session affinity (`DEPLOY.md` section 5).
